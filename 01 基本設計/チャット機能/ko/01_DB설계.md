# 채팅 기능 DB 설계

## 1. 목적

Phase 1 기존 채팅 구조를 유지하면서 Phase 1.5의 프로필, 친구 요청, 친구 관계, 차단 관계를 확장한다.

## 2. 설계 원칙

1. 인증 사용자 기준 엔티티는 기존 `user`를 사용한다.
2. 공개 식별자는 `user.public_id`를 사용한다.
3. 공통 사용자 프로필은 `user_profile`로 분리한다.
4. 친구 요청과 친구 관계를 분리한다.
5. 차단은 방향성 관계로 관리한다.
6. FRIEND 채팅은 기존 `chat_room`, `chat_room_member`를 재사용한다.
7. `room_type`과 `source_type`을 분리한다.
8. Phase 2 오픈 채팅/AI/가상 프로필과 직접 결합하지 않는다.

## 3. 테이블 목록

| 영역 | 테이블 | 설명 |
|---|---|---|
| 사용자 | `user` | 인증 사용자, publicId |
| 사용자 | `user_profile` | 공통 프로필 |
| 소셜 | `friend_request` | 친구 요청 |
| 소셜 | `friend` | 친구 관계 |
| 소셜 | `user_block` | 차단 관계 |
| 채팅 | `chat_room` | 채팅방 |
| 채팅 | `chat_room_member` | 멤버 |
| 채팅 | `chat_message` | 메시지 |
| 채팅 | `chat_message_translation` | 번역 결과 |

## 4. user_profile

| 컬럼 | 설명 | 제약 |
|---|---|---|
| `id` | PK | PK |
| `user_id` | 사용자 ID | FK, UNIQUE |
| `nickname` | 닉네임 | NOT NULL |
| `profile_image_url` | 프로필 이미지 URL | NULL 가능 |
| `bio` | 자기소개/상태 메시지 | NULL 가능 |
| `created_at` | 생성일시 | NOT NULL |
| `updated_at` | 수정일시 | NOT NULL |
| `deleted_at` | 삭제일시 | NULL 가능 |

정책:
- `user`와 논리적 1:1 관계
- publicId는 `user.public_id` 사용
- 현재 이미지는 URL 방식
- 파일 업로드 및 프로필 배경 이미지는 후속 이슈에서 확장
- Phase 2 가상 프로필과 분리

## 5. friend_request

| 컬럼 | 설명 |
|---|---|
| `id` | PK |
| `requester_user_id` | 발신자 |
| `receiver_user_id` | 수신자 |
| `status` | 요청 상태 |
| `requested_at` | 요청 일시 |
| `responded_at` | 응답/취소 일시 |
| `created_at` | 생성일시 |
| `updated_at` | 수정일시 |
| `deleted_at` | 삭제일시 |

상태:
- `PENDING`
- `ACCEPTED`
- `REJECTED`
- `CANCELED`

정책:
- 자기 자신 요청 금지
- 이미 친구인 사용자 요청 금지
- 동일 관계의 PENDING 중복 금지
- 양방향 중 어느 쪽이라도 차단 관계가 있으면 요청 금지
- 수락 시 친구 관계 생성
- 거절/취소는 이력 유지 후 상태 변경

## 6. friend

| 컬럼 | 설명 |
|---|---|
| `id` | PK |
| `user_id` | 기준 사용자 |
| `friend_user_id` | 친구 사용자 |
| `created_at` | 생성일시 |
| `updated_at` | 수정일시 |
| `deleted_at` | 삭제일시 |

정책:
- 서비스 관점에서 논리적 양방향 관계
- 동일 `user_id`, `friend_user_id` 조합 중복 금지
- 조회/삭제 시 양방향 관계를 일관되게 처리
- 요청 수락 시 생성
- 친구 삭제 후 기존 방/메시지는 삭제하지 않음

## 7. user_block

| 컬럼 | 설명 |
|---|---|
| `id` | PK |
| `blocker_user_id` | 차단한 사용자 |
| `blocked_user_id` | 차단된 사용자 |
| `created_at` | 생성일시 |
| `updated_at` | 수정일시 |
| `deleted_at` | 삭제일시 |

정책:
- 자기 자신 차단 금지
- 동일 사용자 중복 차단 금지
- active `(blocker_user_id, blocked_user_id)` 중복 방지
- 친구 요청 제한
- FRIEND DIRECT 신규 시작 제한
- GROUP 멤버 추가 제한
- 차단 시 친구 목록에서 제외
- 해제 후 친구 관계 자동 복구 안 함을 기본으로 함

## 8. 기존 채팅 테이블 연결

### chat_room
주요 논리 필드:
- `room_type`: `DIRECT`, `GROUP`
- `source_type`: `MANUAL`, `FRIEND`, 향후 `OPEN`, `AI`
- `name`
- `description`
- `owner_id`
- `active`

### chat_room_member
- 방과 사용자 멤버십
- `OWNER`, `MEMBER`
- FRIEND GROUP 생성자는 OWNER, 선택 친구는 MEMBER

### chat_message
- 원문 메시지
- 발신자 정보
- cursor pagination 기준

### chat_message_translation
- 메시지별 언어별 번역
- `PENDING`, `COMPLETED`, `FAILED`

## 9. FRIEND DIRECT 연결

```text
friend 관계 확인
      ↓
chat_room
  room_type = DIRECT
  source_type = FRIEND
      ↓
chat_room_member
  user A
  user B
```

- 대상은 친구여야 함
- 양방향 차단 관계 없어야 함
- 동일 사용자 조합 + DIRECT + FRIEND 기존 방 재사용
- MANUAL DIRECT는 별개 방

## 10. FRIEND GROUP 연결

```text
친구 B/C 선택
      ↓
친구/차단 관계 검증
      ↓
chat_room
  room_type = GROUP
  source_type = FRIEND
      ↓
A = OWNER
B/C = MEMBER
```

- 모든 대상은 현재 친구
- 차단 관계 사용자 포함 불가
- 로그인 사용자는 서버에서 OWNER 추가
- Phase 1.5에서는 동일 멤버 구성 그룹 중복 생성 허용

## 11. 주요 정합성 기준

- `user_profile.user_id` UNIQUE
- active friend 조합 중복 방지
- active user_block 조합 중복 방지
- 자기 자신 대상 요청/차단 금지
- 동일 관계 PENDING 중복 방지
- FRIEND DIRECT 재사용 기준: 사용자 조합 + DIRECT + FRIEND
- 방별 동일 사용자 멤버 중복 금지
