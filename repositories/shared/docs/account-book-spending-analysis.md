# 가계부 AI 소비 분석 정책과 저장 계약

가계부 그래프 아래의 분석 카드는 선택 기간의 실제 구매 내용과 이전 구매 맥락을 읽고, 다음 소비에서 바꿀 선택을 제안한다. 사용자는 추가 설명을 입력해 재분석할 수 있으며, 성공한 분석은 같은 기간이라도 매번 별도 이력으로 저장한다.

## 분석 정책

`purchase-context-v4`는 알려진 구매 사실, 조건부 AI 의견, 다음에 바꿀 행동을 분리한다. 비슷한 역할의 상품을 함께 산 경우에도 선물·다른 공간·고장 교체 등의 목적을 단정하지 않는다. 취미 전체를 포기하라는 일반론보다 어떤 역할을 남기고 어떤 추가 선택을 줄일지 설명한다. 질문, 영수증 확인 숙제, 근거 없는 중복 결제 의심으로 보고서를 채우지 않는다.

의료·주거·통근·기본 식사·업무와 학습 도구를 일반 절감 대상으로 삼지 않는다. 점포명과 큰 금액만 있는 거래는 불필요한 구매로 판단하지 않는다. 사용자 설명에 근거가 생기면 그 설명을 반영하되, 이전 조언이 있다는 사실만으로 실제 실천이나 성공·실패를 주장하지 않는다.

분석 생성 후 한 번의 의미 검토로 상품·목적·이전 구매·행동의 일관성을 확인한다. 현재와 과거 거래의 참조, 중복 참조, 금액 합산, 기간 경계와 질문 포함 여부는 코드에서도 검사한다. 모델 검토가 모든 해석의 정확성을 보장하는 것은 아니므로 근거 거래를 함께 제공한다.

가계부 생성·검토 작업만 `SPENDING_COACH` 정책을 사용하며 모델은 `gpt-6.1-sol`, reasoning effort는 `medium`이다. 다른 번역·음성·영수증 작업의 모델 선택은 변경하지 않는다. 모델 기능의 기준은 [OpenAI 공식 모델 문서](https://developers.openai.com/api/docs/models/gpt-6.1-sol)다.

## 기간 선택

| 종류 | 필수 기간 필드 | 범위 |
| --- | --- | --- |
| `MONTHLY` | `year`, `month` | 해당 달 전체 |
| `QUARTERLY` | `year`, `quarter` | 달력 기준 1~4분기 |
| `HALF_YEARLY` | `year`, `half` | 상반기 1~6월 또는 하반기 7~12월 |
| `YEARLY` | `year` | 해당 연도 전체 |
| `CUSTOM` | 시작 연도의 `year`, `startDate`, `endDate` | 시작일과 종료일을 포함한 최소 한 달 |

종류와 관계없는 기간 필드는 보내지 않는다. 연도는 2000~9998이다. 사용자 종료일은 포함하며, 내부 응답과 AI 입력은 `periodEndExclusive`로 표현한다. 한 달은 시작일에 달력 한 달을 더한 경계까지이며, 말일은 다음 달 말일로 보정한다. 예를 들어 2026-01-31부터 2026-02-27까지는 내부 종료 경계가 2026-02-28이므로 유효하다.

현재 기간의 지출과 시작일 전 최대 12개월의 구매를 읽는다. 미래 거래와 겹치는 기간의 분석 이력은 과거 맥락으로 넣지 않는다. 현재 상세는 최대 6,000건과 텍스트 예산 안에서 준비하며, 일부만 제공한 경우 `coverage.isPartial`과 사유를 명시한다. 같은 구매 정보의 반복 행은 입력에서 묶어 표현하되 출력의 근거는 원본 거래 전체로 복원한다. 과거의 긴 광고 문구를 축약한 경우 별도 표시한다.

## 예상 절약액

예상액은 선택 기간에 제안을 적용했다면 줄일 수 있었을 가상 금액이다. 실제 절약 실적이나 통계적 신뢰구간으로 표현하지 않는다. 현재 근거 중 `savingsTransactionRefs`로 지정한 구매만 계산하며, 설명용 구매와 이전 구매는 합산하지 않는다. 두 조언이 같은 구매를 중복 계산할 수 없다.

| 시나리오 | 구매 감소 가정 | 감소액 중 대체 비용 가정 |
| --- | --- | --- |
| `SKIP_EXTRA_ITEM` | 독립적으로 가격이 확인되는 대상 구매 전체 100% 생략 | 0% |
| `SMALLER_SELECTION` | 대상 구매 금액의 5~15%를 덜 선택 | 0~30% |
| `DRINK_REPLACEMENT` | 명확한 선택적 음료 구매의 10~20%를 대체 | 50~80% |

위 비율은 효과를 측정한 수치가 아니라 규모를 살펴보기 위해 고정한 가정이다. `SKIP_EXTRA_ITEM`은 혼합 구매에서 가격을 모르는 한 품목을 빼는 경우에 사용할 수 없다. 일부 조정의 가정과 예외, 대체 비용을 함께 표시하며 산정 근거가 부족하면 예상 합계에서 제외한다. 표본 분석에서는 전체 기간의 절약액으로 확대하지 않는다.

금액은 10진 문자열로 전달하고 통화 소수 자릿수로 반올림한다. 중간 예상액은 구매 감소 중간값에서 대체 비용 중간값을 뺀다. 하한은 최소 감소·최대 대체 비용, 상한은 최대 감소·최소 대체 비용으로 계산한다. BE가 실제 대상 거래 금액으로 다시 계산하므로 공급자가 보낸 금액을 그대로 신뢰하지 않는다. 합계는 서로 겹치지 않는 시나리오만 더한다.

## API와 분석 이력

인증된 가계부 접근권한을 생성·저장·목록·상세 조회 시 확인한다.

| API | 동작 |
| --- | --- |
| `GET /api/v1/account-books/{id}/spending-analysis/snapshot` | 기간의 지문·거래 수·총지출 조회 |
| `POST /api/v1/account-books/{id}/spending-analysis` | 명시적 생성 또는 재분석 후 새 이력 저장 |
| `GET /api/v1/account-books/{id}/spending-analysis/history?page=0&size=10` | 생성 시각 역순의 이력 목록 |
| `GET /api/v1/account-books/{id}/spending-analysis/history/{analysisId}` | 생성 당시의 결과와 추가 설명 조회 |

생성 요청은 기간 필드, `locale`(`ko`, `ja`, `en`), 선택적인 `comment`(최대 2,000자)를 받는다. 목록 크기는 1~50이다. 재분석은 새 UUID를 생성하며 같은 기간의 기존 행을 갱신하지 않는다. 목록과 상세 조회는 AI를 호출하지 않는다. 자동 재시도로 유료 호출을 반복하지 않는다.

응답은 정책 버전, 기간, 통화, 범위, 요약, 조언, 반영한 코멘트, 생성 시각, 원장 지문, `analysisId`와 예상액을 포함한다. 각 조언에는 의견, 현재·과거 근거 거래와 계산 대상 거래의 생성 당시 스냅샷을 저장한다. 저장된 결과는 이후 원장 수정으로 바꾸지 않으며, 현재 지문과 다르면 오래된 결과임을 표시한다. 화면에서 근거 거래는 기존 거래 카드·표 형식으로 읽고 상세보기만 허용한다.

AI 호출 중에는 DB 트랜잭션을 유지하지 않는다. 결과 저장 전에 원장 지문과 접근권한을 다시 확인하며 변경된 원장은 `409 STALE_SNAPSHOT`으로 처리한다. 분석은 대기까지 포함해 240초, BE의 AI 서버 요청은 250초로 제한한다. 분석 경로를 중계하는 프록시도 해당 예산을 지원해야 한다.

웹의 분석 생성·스냅샷·이력 목록·이력 상세 네 경로는 공개 build 변수 `NEXT_PUBLIC_ACCOUNT_BOOK_ANALYSIS_API_URL`로 별도 HTTPS API base(`/api/v1` 포함)를 지정할 수 있다. 미설정·빈 값이면 기존 `NEXT_PUBLIC_API_URL`을 사용하며, 다른 업무 API와 서버 인증용 `API_URL`은 유지한다. 지정한 값은 HTTPS·`/api/v1` 경로여야 하고 자격증명·쿼리·fragment를 포함할 수 없다. 기존 `apiClient`의 세션·권한·취소 처리를 통과한 뒤 주소만 선택한다.

운영의 분석 전용 값은 `https://217.142.230.186/api/v1`이다. 배포 담당이 이 원점의 신뢰 가능한 TLS와 네 경로의 CORS·OPTIONS 및 260초 중계 예산을 검증한 뒤 Production build에 변수를 설정하고 FE를 빌드한다. runtime 변수만 바꾸어 기존 browser bundle이 갱신됐다고 간주하지 않는다. 원점 변경 시에는 명시한 build 설정도 함께 갱신한다.

## 저장과 운영 반영

`scripts/sql/20261105_account_book_spending_analysis.sql`의 `account_book_spending_analysis` 테이블이 필요하다. 가계부 ID, 생성자 ID, 생성 시각과 결과 JSON을 저장하고, 가계부별 생성 시각 조회를 인덱스로 지원한다. 가계부가 물리 삭제되면 외래키로 분석 이력도 삭제한다.

이력에는 거래와 코멘트가 들어 있으므로 가계부 데이터와 같은 접근 범위와 보관 기준을 적용한다. 입력·공급자 응답 원문·키를 오류 본문이나 일반 로그에 남기지 않는다. 거래 필드와 코멘트는 분석 대상 데이터이며 시스템 지시로 실행하지 않는다.

분석 생성·스냅샷·이력 목록·상세 경로의 일반 HTTP 로그는 `SPENDING_ANALYSIS_REDACTED`로 요청·응답 본문과 사용자·장부·분석 식별자를 가린다. 실패 진단은 BE의 요청 구성·전송·응답 확인·역직렬화 단계, AI의 문맥 준비·생성·검토·결과 검증 단계와 고정 오류코드·HTTP 상태·경과시간·예외 클래스만 기록한다. AI 스키마의 enum 개수와 구매 묶음 건수는 숫자로 기록하며 예외 메시지·traceback·입력·외부 응답 원문은 기록하지 않는다.

운영 반영은 배포 담당 채팅에서 migration과 AI·BE 계약의 전환 순서를 확인해 수행한다. 개발 검증 환경에서는 운영 원장을 읽기 전용 드라이버로 연결하고 새 이력만 별도의 로컬 H2에 저장한다. 이 로컬 분리는 운영 migration을 실행한 근거가 아니다.

## 순차 시뮬레이션의 해석

초기 달을 분석한 다음 달부터 조언을 일부 반영한 가상 지출을 만들고, 그 지출을 다시 분석한다. 현재 기간에 제안을 적용했을 예상액과 이후 달의 누적 가상 차이를 별도 지표로 둔다. 원본 거래는 수정하지 않는다.

실천율·적용 가능한 구매 역할·조언 만료 기간에 따라 가상 차이가 달라진다. 같은 역할의 후속 구매가 드문 경우에는 유용한 일회성 제안이 있어도 이후 달의 차이가 작다. 따라서 시뮬레이션 절약액의 크기만으로 분석 방식을 선택하거나 실제 장기 효과를 입증했다고 주장하지 않는다. 근거의 정확성, 구체적인 소비 선택과 설명 반영을 함께 검토한다.

## 日本語 家計簿AI消費分析の方針と保存仕様

家計簿のグラフ下にある分析カードは、選択期間の実際の購入内容と過去の購入経緯を読み取り、次の消費で見直せる選択を提案する。利用者は補足を入力して再分析でき、成功した分析は同じ期間でも毎回別の履歴として保存する。

### 分析方針

`purchase-context-v4`は、記録から分かる購入の事実、条件付きのAIの見解、次に変える行動を分けて示す。似た役割の商品を一緒に購入していても、贈り物、別の部屋用、故障による買い替えなどの目的を決めつけない。趣味全体を諦めるという一般論より、どの役割を残し、どの追加の選択を控えるかを説明する。質問、レシート確認の宿題、根拠のない二重決済の疑いで報告を埋めない。

医療、住居、通勤、基本的な食事、仕事や学習の道具を一般的な削減対象にしない。店舗名と大きな金額しか分からない取引は、不要な購入と判断しない。利用者の説明から根拠が得られた場合はその説明を反映するが、過去の助言があるだけで、実際の実践や成功・失敗を主張しない。

分析を生成した後、一度の意味検証で商品、目的、過去の購入、行動の整合性を確認する。現在と過去の取引参照、参照の重複、金額の合算、期間の境界、質問の有無はコードでも検査する。モデルによる検証がすべての解釈の正確性を保証するわけではないため、根拠となる取引も提示する。

家計簿の生成・検証処理だけが`SPENDING_COACH`方針を使用し、モデルは`gpt-6.1-sol`、reasoning effortは`medium`とする。ほかの翻訳、音声、レシート処理のモデル選択は変更しない。モデル機能の参照先は[OpenAI公式モデル文書](https://developers.openai.com/api/docs/models/gpt-6.1-sol)とする。

### 期間選択

| 種別 | 必須の期間フィールド | 範囲 |
| --- | --- | --- |
| `MONTHLY` | `year`, `month` | 対象月全体 |
| `QUARTERLY` | `year`, `quarter` | 暦に基づく第1〜4四半期 |
| `HALF_YEARLY` | `year`, `half` | 上半期の1〜6月、または下半期の7〜12月 |
| `YEARLY` | `year` | 対象年全体 |
| `CUSTOM` | 開始年の`year`, `startDate`, `endDate` | 開始日と終了日を含む、最低でも暦でひと月の期間 |

選択した種別と関係のない期間フィールドは送信しない。年は2000〜9998とする。利用者が指定した終了日は期間に含め、内部の応答とAI入力では`periodEndExclusive`で表す。ひと月は、開始日に暦でひと月を加えた境界までとし、月末の日付は翌月の末日に補正する。例えば、2026-01-31から2026-02-27までは内部の終了境界が2026-02-28になるため有効である。

現在の期間の支出と、開始日より前の最大12か月の購入を読む。未来の取引と、現在の期間に重なる分析履歴は、過去の文脈に含めない。現在の詳細は最大6,000件とテキスト予算の範囲内で準備し、一部だけを提供した場合は`coverage.isPartial`とその理由を明示する。同じ購入情報の繰り返し行は入力時にまとめて表すが、出力の根拠は元の取引全件に復元する。過去の長い広告文を短縮した場合は、その旨を別途表示する。

### 削減見込み額

見込み額は、選択期間に提案を取り入れていた場合に削減できた可能性がある仮想の金額である。実際の節約実績や統計的な信頼区間としては表現しない。現在の根拠のうち、`savingsTransactionRefs`で指定した購入だけを計算し、説明のための購入と過去の購入は合算しない。異なる助言が同じ購入を重複して計上することはできない。

| シナリオ | 購入を減らす仮定 | 減らした金額に対する代替費用の仮定 |
| --- | --- | --- |
| `SKIP_EXTRA_ITEM` | 個別の価格が確認できる対象購入を全て見送る（100%） | 0% |
| `SMALLER_SELECTION` | 対象購入額の5〜15%を控える | 0〜30% |
| `DRINK_REPLACEMENT` | 内容が明確な嗜好飲料の購入額の10〜20%を代替する | 50〜80% |

これらの比率は効果の測定値ではなく、規模を検討するために固定した仮定である。`SKIP_EXTRA_ITEM`は、複数の商品が混在する購入から個別価格が不明な商品だけを除く場合には使えない。一部を調整する仮定、例外、代替費用を併記し、算定根拠が不足する場合は見込み額の合計から除外する。標本による分析を、期間全体の削減額に拡大しない。

金額は10進数の文字列で渡し、通貨の小数桁に合わせて四捨五入する。中間の見込み額は、購入減少額の中間値から代替費用の中間値を差し引く。下限は最小の購入減少と最大の代替費用、上限は最大の購入減少と最小の代替費用で計算する。BEが実際の対象取引額を使って再計算するため、プロバイダーが返した金額をそのまま信用しない。合計には対象が重複しないシナリオだけを加える。

### APIと分析履歴

生成、保存、一覧、詳細の各処理で、認証済みの家計簿アクセス権限を確認する。

| API | 動作 |
| --- | --- |
| `GET /api/v1/account-books/{id}/spending-analysis/snapshot` | 期間のフィンガープリント、取引数、支出総額を取得する |
| `POST /api/v1/account-books/{id}/spending-analysis` | 明示的な生成または再分析を行い、新しい履歴を保存する |
| `GET /api/v1/account-books/{id}/spending-analysis/history?page=0&size=10` | 生成時刻の降順で履歴を一覧表示する |
| `GET /api/v1/account-books/{id}/spending-analysis/history/{analysisId}` | 生成当時の結果と補足を取得する |

生成リクエストは期間フィールド、`locale`（`ko`、`ja`、`en`）、任意の`comment`（最大2,000文字）を受け取る。一覧の取得件数は1〜50とする。再分析は新しいUUIDを生成し、同じ期間の既存行を更新しない。一覧と詳細の取得ではAIを呼び出さない。自動再試行によって有料呼び出しを繰り返さない。

応答には、方針のバージョン、期間、通貨、対象範囲、要約、助言、反映したコメント、生成時刻、元帳のフィンガープリント、`analysisId`、見込み額を含める。各助言には、見解、現在と過去の根拠取引、計算対象取引の生成当時のスナップショットを保存する。保存済みの結果を後の元帳修正で書き換えず、現在のフィンガープリントと異なる場合は古い結果であることを表示する。画面では既存の取引カード・表形式で根拠取引を表示し、操作は詳細表示だけに限定する。

AI呼び出し中はDBトランザクションを維持しない。結果の保存前に元帳のフィンガープリントとアクセス権限を再確認し、元帳が変更されていた場合は`409 STALE_SNAPSHOT`として扱う。分析は待機を含めて240秒、BEからAIサーバーへのリクエストは250秒に制限する。分析経路を中継するプロキシも、この時間枠に対応する必要がある。

Webの分析生成・スナップショット・履歴一覧・履歴詳細の4経路は、公開build変数`NEXT_PUBLIC_ACCOUNT_BOOK_ANALYSIS_API_URL`で個別のHTTPS API base（`/api/v1`を含む）を指定できる。未設定・空白の場合は既存の`NEXT_PUBLIC_API_URL`を使用し、ほかの業務APIとサーバー認証用`API_URL`は維持する。指定値にはHTTPS・`/api/v1`を使い、認証情報・クエリ・fragmentを含めない。既存の`apiClient`によるセッション・権限・キャンセル処理を通過した後、接続先だけを選ぶ。

本番の分析専用値は`https://217.142.230.186/api/v1`とする。デプロイ担当がこの接続先の信頼できるTLS、4経路のCORS・OPTIONS、260秒の中継時間枠を検証してからProduction buildに変数を設定し、FEをビルドする。runtime変数の変更だけで既存のbrowser bundleが更新されたとは扱わない。接続先を変える場合は明示したbuild設定も更新する。

### 保存と本番反映

`scripts/sql/20261105_account_book_spending_analysis.sql`の`account_book_spending_analysis`テーブルを必要とする。家計簿ID、生成者ID、生成時刻、結果JSONを保存し、家計簿ごとの生成時刻による検索をインデックスで支援する。家計簿が物理削除された場合は、外部キーによって分析履歴も削除する。

履歴には取引とコメントが含まれるため、家計簿データと同じアクセス範囲と保管基準を適用する。入力、プロバイダー応答の原文、キーをエラー本文や通常のログに残さない。取引フィールドとコメントは分析対象のデータであり、システムへの指示として実行しない。

分析生成・スナップショット・履歴一覧・詳細経路の通常HTTPログは`SPENDING_ANALYSIS_REDACTED`でリクエスト・レスポンス本文と利用者・家計簿・分析の識別子を伏せる。失敗診断には、BEのリクエスト構成・送信・応答確認・デシリアライズ段階、AIの文脈準備・生成・検証・結果確認段階と固定エラーコード・HTTP状態・経過時間・例外クラスだけを記録する。AIスキーマのenum数と購入グループ数は数値で記録し、例外メッセージ・traceback・入力・外部応答の原文は記録しない。

本番反映は、デプロイ担当チャットでmigrationとAI・BE契約の切り替え順序を確認して実施する。開発検証環境では、本番の元帳を読み取り専用ドライバーで接続し、新しい履歴だけを別のローカルH2に保存する。このローカル環境の分離は、本番のmigrationを実行済みであることを示すものではない。

### 順次シミュレーションの解釈

最初の月を分析した翌月から助言を一部取り入れた仮想支出を作り、その支出を再分析する。当該期間に提案を適用した場合の見込み額と、その後の月の累積仮想差額を別の指標とする。元の取引は変更しない。

実践率、適用できる購入の役割、助言の有効期限によって仮想の差額は変わる。同じ役割の後続購入が少ない場合は、有用な一回限りの提案があっても、その後の月の差額は小さい。そのため、シミュレーションの削減額の大きさだけで分析方式を選んだり、実際の長期効果を立証したと主張したりしない。根拠の正確性、具体的な消費の選択、補足の反映を併せて検討する。
